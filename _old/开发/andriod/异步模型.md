# 1. 同步异步
Appache Tomcat 采用的是线程模型(多线程工作方式)，如下图：
 
[tomcat 线程模型](/static/开发/andriod/imgs/tomcat_1.png)

接收者线程接收客户端的HTTP请求，然后将这些请求分配给请求处理线程进行处理；
Tomcat中接收到多个请求的时候，会为每一个连接分配一个线程，然后再由这些线程区执行相应的操作；
接收者线程(acceptor thread) 接收客户端的HTTP请求，然后将这些请求分配给请求处理线程进行处理，
会为每个连接分配一个线程，然后再由这些线程区执行相应的操作，在Tomcat分配的线程中的执行的时候，每当执行到IO操作时，
程序期间会处于等待状态，同时该线程会处于挂起状态，也就是该线程不能执行其他操作，而必须等待响应结果返回之后才能继续执行；

等待IO操作完成后才能继续执行，这种方式称为同步调用，同时我们也能看到线程被挂起；也就是线程没有被执行就是阻塞。

同步和阻塞时两个不同的概念，他不指的是一个行为，当执行IO操作时，在代码层面我们需要主动去等待执行结果，知道结果返回，
而阻塞值得是一种状态，当执行IO操作时线程处于挂起状态。
所以同步不是阻塞；同步也可以是是非阻塞状态； 比如我们去执行同步代码块的时候，线程可以不阻塞而是一直在后台运行。
同步描述的是一种行为，而阻塞面熟的是一种状态；

# 1.1 回调地狱
 在代码层面，我们往往会用回调来进行IO操作，但是当处理的逻辑比较复杂时 ，回调就会一层层嵌套，最终出现我们常见的回调地狱。
 回调的逻辑比用同步实现相比要复杂的多，而且不容易维护；
 
 # 2. Kotlin 的Coroutine
 引入了协程(Coroutine)来支持更好的异步操作，利用它我们可以避免在异步编程中使用大量的回调，相比传统的多线程技术，它更容易提升系统的高并发处理能力；
 协程是一个无优先级的自程序调度组件，运行子程序在特定的地方挂起和恢复；
 只要有足够的内存，一个线程中可以有任意多个协程，但某一时刻只能有一个协程在运行，多个协程分析该线程分配道德计算机资源；
 
 ```
 GlobalScope.launch{	//后台启动一个协程
	delay(1000L)
	println("World")   //延迟输出
 
 }
 pritln("Hello,")
 Thread.sleep(2000L) 	//为了使JVM保活，阻塞主线程3s
 ```
 线程是由操作系统调度的，当操作系统切换线程时，会产生一定的消耗，
 协程包含于线程中，即协程工作在线程之上，协程切换可由程序来自己控制；
 
 - delay 只能在协程内部使用，用于挂起协程，不会阻塞线程；
 - sleep 用于阻塞线程；
 
 混用delay和sleep不容易弄清那个时阻塞式的，那个式非阻塞式的，改善上述代码,引入了runBlocking：
 ```
 //全部用非阻塞式的
  fun main(args:Array<String>)= runBlocking{
	launch{
		delay(1000L)
		println("World")   //延迟输出
	}
	pritln("Hello,")
	delay(2000L)   		 //2s内保活
 }
 ```
 ```
 fun main(args:Array<String>)= runBlocking{
	repeat(100_1000){
		launch{
			println("Hello")
		}
	}
 }
 ```
 启动了10万个协程去执行输出“hello” 的操作，但是如果我们启动10万个线程去做，就可能会出现“out of memory”的错误；
 
 ## 2.1 runBlocking 和launch
 两个函数都启动一个协程：
 - runBlocking 最高级协程，即 主协程， 会阻塞当前执行的线程；
 - launch 创建的协程能够在 runBlocking 中运行，反之不可
 
 ## 2.2 协程的生命周期于join
 上面我们使用 delay 或 sleep 来保活线程；，但是我们执行IO操作时并不知道该操作要执行多久：
 ```
 fun main()=funBlocking{
	 val job=launch{
		search()
	 }
	 println("Hello,")
	 job.join() 		//程序一直等待，直到启动的协程结束； 
 }
 susend fun search(){
	delay(1000L)
	println("World")
 }

 ```
 为了让程序执行完一直保活，我们使用join。
 - suspend 修饰的方法在协程内部使用时和普通方法没有区别，
   不同的是在suspend修饰的方法内部还可调用其他suspend方法；
	比如上面的search方法，调用了 delay就是 suspend方法；这些方法只能在协程内部或其他suspend方法中执行；
	不能再普通方法中执行；
	
## 2.3 协程实现异步代码
协程中的执行顺序：
```
susend fun searchItemOne():String{
	delay(1000L)
	return "item-one"
}

susend fun searchItemTwo():String{
	delay(1000L)
	return "item-two"
}

fun main(args:Array<String>=runBlocking<Unit>{
	val one=searchItemOne()
	val two=searchItemTwo()
	println("this items is ${one} and ${two}")
}
```
执行两个查询操作，协程内部其实是顺序执行的，即先执行searchitemOne，在执行searchItemWto,
顺序执行其实是不合理的，因为这两个操作它们没有相互依赖的关系；为了让Kotlin中的两个操作并行执行，我们可以使用
`async`与`await`，如下：
```
fun main(args:Array<String>=runBlocking<Unit>{
	val one=async {searchItemOne()}
	val two=async{searchItemTwo()}
	println("this items is ${one.await()} and ${two.await()}")
}
```
- async 相当于创建了一个子协程，它和其他子协程一起并行工作；
- 与lauch不同的是，async会返回一个`Deferred`对象
	Deferred值是一个非阻塞可取消的future【将来会返回一个结果 】，是一个带有结果的job；
	lauch也会返回一个job对象，但没有返回值
- await 等到结果获取到；

注意： 协程不是万能的，不能去滥用协程，滥用协程可能会使得代码变得更加复杂，不利于后期维护；

## 2.3 共享资源控制
### 2.3.1 锁模式
一段代码可以由很多线程执行，那么存在两个甚至更多个线程对共享资源进行操作，则可能会导致共享资源不一致的问题；
java中给代码加锁，常用的就是使用关键字 synchronized关键字；可作用再方法或代码块上，
Kotlin使用@synchronized和synchronized() 来实现等同的效果；
```
class Shop{
	val goods = hashMapOf<Long,Int>()
	init{
		goods.put(1,10)
		goods.put(2,15)
	}
	@Synchronized fun buyGoods(id:Long){
		val stock = goods.getValue(id)
		goods.put(id,stock-1)
	}
	fun buyGoods(id:Long){
		synchronized(this){
			val stock=goods.getValue(id)
			goods.put(id,stock-1)
		}
	}
}

```

- 有时候[并发激烈]性能表现很一般；
	在竞争不激烈情况时，使用synchronized相对来说更加简单，更加语义化；
- 过早的优化是万恶之源；

Kotlin还支持其他一些并发工具，比如volatile，Kotlin做了些改造，volatile变成了注解；
```
@Volatile privater var running=false
```

除了上面方法外java还可以使用Lock方式来对代码进行加锁：
```
var lock:Lock=ReentrantLock()
fun buyGoods(id:Long){
	lock.lock()
	try{
		val stock=goods.getValue(id)
		goods.put(id,stock-1)
	} catch(ex:Exception){
		println("${ex}")
	}finally{
		lock.unlock()
	}
}
```
- 在同一个类有多个同步方法，将会竞争同一把锁；
- 加锁后编码人员很容易忘记解锁操作；
- 重复的模板代码

改进 Kotlin 相应的方法；
```
fun <T> withLock(lock:Lock,action:()->T):T{
	lock.lock()
	try{
		return action()
	} catch(ex:Exception){
		println("${ex}")
	}finally{
		lock.unlock()
	}
}
```

使用：
```
var lock:Lock=ReentrantLock()
lock.withLock {buyGoods(1)}
```

## 2.4 Actor 有状态的并行计算单元
Actor 概念已经存在很久，于1973年提出，直到Erlang中应用后才逐渐被大众所熟知，
现在Actor已经用于生产环境中，比如Akka(基于Actor模型的并发框架)，另外还有很多语言都支持Actor模型
比如：Java、Scala，包括Kotlin也内置了Actor模型：

Actor所作的事情很简单：
- 用另一种死来来解决并发问题，而不是只有共享内存这一种方式；
- 提高锁抽象的程度，尽量不在业务中出现锁，减少因为使用锁出现的问题，比如死锁；
- 为解决分布式并发问题提供一种更好的思路；

举个简单例子：
假定现实中的两个人，它们只知道对方的地址，他们向要交流，给对方传递信息，
但又没有手机电话网络之类的途径，所以他们只能用信件传递消息。很想现实中的邮政系统；
上述例子中的信件相当于Actor中的消息，Actor和Actor之间只能通过消息来通讯；

[Actor系统](/static/开发/andriod/imgs/actor.png)

不同人之间的邮件投递可以并行处理，反映到应用中，就是可以利用多核的处理器；
另外**信件信息是不可改变的**，同时接收信件的人是从它的信箱李有序地处理信件，
这两点就可保证信息的一致性，不再需要使用共享内存。
顺序地处理消息，Actor内部的状态将不会有线程安全问题；

使用Actor 必须满足以下两条原则：
- 消息的发送必须现宇消息的接收；
- 同一个Actor对一条信息的处理优于对下一条消息的处理；

## 2.5 CQRS架构
一种命令于查询职责分离的设计原则，与普通的读写分离有一些区别，主要体现在写方面，它不再是对记录进行不断修改，而是一种事件朔源的思维方式；
与数据库备份所说的binlog方案很像，数据库会将有修改状态行为的sql执行情况一条条记录在binlog日志中，利用这些记录便能推到处最终状态；
### 2.5.1 EventSourcing事件朔源

记录对象的操作轨迹，事件朔源的关键点：
- 以事件为驱动，任何用户行为都是一种事件
	将事件行为都生命在Action类中，通过这种方式就可以将业务行为分成各种事件，利用事件驱动的方式构造业务逻辑，不仅语义上更加清晰，同时还天然支持异步操作；
	使用异步架构可以较为容易地提升程序的吞吐量；
- 存储所有对于对象状态会有影响的事件[非常重要，因为我们在程序恢复或数据校验时需要它]
	聚合、根聚合，聚合顾名思义是一系列对象的集合，而聚合根属于这个聚合中可以被外部访问的元素；
	事件朔源这些设计，我们就要用一种新的思维模式去设计我们的业务，只能通过聚合根来操作聚合中其他对象的状态；
	比如原来你可能直接在数据库中更改一下商品的库存便可以了，现在你需要向商家发一条修改商品库存的信息，然后它会生成一个库存修改的事件，最后才会修改好库存(修改聚合里面对象的状态也可以修改数据库中的记录)
	简单操作反而变复杂有何益处？传统的方法修改错误，修改内容无法回滚，回滚需要付出极大代价。
	如果通过一个聚合根来修改聚合中对象状态，那么这一切将会变得容易；
- 用于查询或显示的视图数据不一定序持久化，比如我们将对象的状态数据存放在内存中；
