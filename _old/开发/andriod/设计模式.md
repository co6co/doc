# 设计模式
Kotlin是一名多范式的语言。

# 1. 创建型
## 1.1 工厂模式
一个工厂同时生成个人电脑和服务器设备，用熟悉工厂模式设计业务逻辑：

### 1.1.1 通过用创建工厂 
```
interfave Computer {
	val cpu:String
}

class PC(override val cpu:String="Core"):Computer
class Server(override val cpu:String="Xeon"):Computer

enum class ComputerType{ PC,Server}

class ComputerFfactory{
	fun produce(type:ComputerType):Computer{
		return when(type){
			ComputerType.PC->PC()
			ComputerType.Server->Server()
			
		}
	}
}

//调用
val com= ComputerFfactory().produce(ComputerType.PC)
```

### 1.1.2 单例创建工厂
```
//用单例替代工厂类
object ComputerFfactory{
	...
}
//调用
val com= ComputerFfactory.produce(ComputerType.PC)

```
### 1.1.3 运算符重载
上面通过传入的ComputerType 参数来创建不同的对象，决定这里的produce显得多余。
Kotlin还支持运算符重载，因此我们可以通过operator操作符重载invoke方法来代替produce 进一步简化：
```
object ComputerFfactory{
	operator fun invoke(type:ComputerType):Computer{
		....
	}
}

//调用
ComputerFfactory(ComputerType.PC)
```
### 1.1.4 伴生类创建静态工厂
我们是否能直接通过 Computer() 而不是通过 computerFactory()来创建实例；
《Effecive Java》 第一条指导原则: **考虑用静态工厂方法代替构造器**
```
interfave Computer{
	val cpu :Sring
	
	companion object {
		operator fun invoke(type:ComputerType):Computer{
			....
		}
	}
}
```

如果你觉得还是Factory这个名字好，也可以用Factory来命名Computer的伴生对象如下：
```
interfave Computer{

	companion object Factory {
		operator fun invoke(type:ComputerType):Computer{
			....
		}
	}
}

//调用
Computer.Factory(ComputerType.PC)
```

## 1.2 抽象工厂
内联函数有个很大的作用，可以**具体化参数类型**，利用这个特性，可以改进抽象工厂。
工厂模式很好的处理一个产品等级结构的问题，
但当问题上升到多个产品等机结构的时候，
比如增加几个不同的电脑品牌，那么就必须增加相应的工厂类，
然而我们并不希望对每个模型都建立一个工厂，这会让代码变得难以维护，
所有这时侯我们就需要引入抽象工厂模式。

定义：**为创建一组相关或相互依赖的对象提供一个接口，且无需指定他们具体类。**

相关和相互依赖的对象称为“产品族”, 上面提到的电脑品牌代表不同电脑品牌的产品族。

```
interface Computer
class Dell：Computer
class Asus：Computer
class Acer：Computer

abstract class AbstractFactory{
	abstract fun produce():Computer
	companion object{
		operator fun invoke(factory:AbstractFactory):AbstractFactory{
			return factory
		}
	}
}
class DellFactory:AbstractFactory(){
	override fun produce()=Dell()
}

class AsusFactory:AbstractFactory(){
	override fun produce()=Asus()
}

class AcerFactory:AbstractFactory(){
	override fun produce()=Acer()
}
```

当你每次创建具体的工厂时，都需要传入一个具体的工厂类对象作为参数，
这个语法上显得不够优雅，我们可以利用kotlin的内联函数来改善这种情况：
```
inline operator fun <reified T:Computer>:invoke():AbstractFactory =when(T::class.java){
	Dell::class->DellFactory()
	...
	else -> throw IllegalArgumentException()
}
```

## 1.3 建造者模式（多参数对象创建问题）
将一个复杂对象的构建与它的表示分离，使得同样的构建过程可以创建不同的表示。

工厂模式和构造函数都存在相同的问题，不能很好的扩展到**大量的可选参数**。

假如有个机械人类，它含有多个属性：代号、名字、电池、重量、高度、速度、声音等。
但是很多产品都不具有其中的某些属性；

一种糟糕的设计就是将所有参数都放在构造函数里，也可能采用**重叠构造器模式(telescoping constructor) **即先提供一个只有必要参数的构造函数，
然后再提供其他更多的构造函数，虽然这种模式在调用的时候改进了不少，但随着构造函数的参数增加，很快就会失去控制，代码变得难以维护；

## 1.3.1 构造者模式
构建者模式可以避免以上的问题：
```
class Robot private constructor(
	val code:String,
	val battery:String?,
	val height:Int?
	val weight:Int?){
		class Builder(val code:String){
			private var battery:String?=null
			private var height:Int?=null
			privatevar weight:Int?=null
			
			fun setBattery(battery:String?):Builder{
				this.battery=battery
				return this
			}
			
			...
						
			fun build():Robot{
				//完整参数
				return Robot(code,battery,height,weight)
			}
		}
	}
	

//调用方式
val robot=Robot.Builder("007")
		.setBattery("R6")
		...
		.build()
```

- Robot 内部定义了一个嵌套类Builder ，由它负责创建Robot对象；
- Robot 的构造函数用private修饰，确保使用者无法直接通过Robot声明；
- 通过Builter类定义的set方法对可选属性进行设置；
- 最终调用 build方法来返回Robot对象；

有点类型于：**柯里化语法**

### 1.3.2 具名参数
构造者模式存在的问题：
- 业务参数很多，代码依然会显得冗长；
- 可能会忘记调最后的build方法；
- 创建对象时需要先创建构造器，额外增加了多余的开销；

《Effecive java》针对建造者模式的描述：
本质上builder模式模拟了具名的可选参数，就像Ada和Python中一样，Kotlin也拥有具名可选参数的编译功能；

```
class Robot(val code:String,val battery:String?=null,...)
```

相比建造者模式，具名参数优点：
- 代码简单；
- 声明对象时，每个参数名都可以是显示的，无需按照顺序；
- 对象参数都有val声明，相比Builder更加安全；

`data class Robot`能把更好的替代`class Robot` 

### 1.3.3. require 方法对参数进行约束

建造者模式的另一个作用 -- 对参数增加约束条件；
假如：一个机械人的重量必须根据电池的型号决定，在未传入电池参数时，
不能对weight属性进行赋值，
```
fun build():Roboot{
	if(weight!=null) && battery ==null{
		throw IllegalArgumenException("...")
	} else{
		return Robot(code ,battery,height,weight)
	}
	
}
```

在Kotlin中我们在类或函数中，可以使用 require 关键字进行函数参数限制，
本质上它是一个内联方法，有点类似于Java 中的assert：
```
class Robot(
	val code:String,
	...
){
	init{
		require(weight==null|| battery !=null){
			"battery should be determined when setting weight."
		}
	}
}

```

# 2. 行为型模式
当我们用创建模式创建出对象后，就需要在不同对象之间划分职责，产生交换。
那些用来识别对象之间的常用交流模式就是行为模式；

## 2.1 观察者模式
在Android诸多设计都是基于观察者模式来实现的： 

观察者模式定义了一个一对多的依赖关系，让一个或多个观察者对象监听一个主题对象，
这样以来，当被观察者状态发生改变时，需要通知相应的观察者，使这些观察者对象能够自动更新；

java自身标准库提供`java.util.Observable` 类和`java.util.Observer` 接口来帮助实现观察者模式；

Kotlin在语法上比java简洁，也可以使用上面的类和接口实现观察者模式：

### 2.1.1 Observable
 
- 版本Observer
	```
	// 可观察者
	class StockUpdate:Observable(){
		var observers=mutableSetOf<Observer>()
		
		fun setStockChanged(price:Int){
			this.observers.forEach{it.update(this.price)}
		}
	}
	//观察者
	class StockDisplay:Observer{
		override fun update(o:Observable,price:Any){
			if(o is StockUpdate){
				println("latest stock price is ${price}.")
			}
		}
	}
	
	
	
	//使用
	val su =StockUpdate()
	val sd =StockDisplay()
	su.observers.add(ad)
	su.setStockChanged(1000)
	```
- 版本Delegates.observable
	```
	import kotlin.properties.Delegates

	interface StockUpdateListener{
		fun onRise(price:Int) 	//价格上升
		fun onFall(price:Int)	//价格下降
	}
	
	class StockUpdate{
		var listeners=mutableSetOf<StockUpdateListener>()
		
		//委托属性，当属性发生变化时 触发后面委托观察者
		var price:Int by Delegates.observable(0){_/*委托属性的元数据KProperty对象*/,old,new->{
			listeners.forEach{
				if(new >old) it.onRise(price) else it.onFall(price)
			}
		}
		
		}
	}
	
	class StockDisplay:StockUpdateListener{
		override fun onRise(price:int){
			println("risen to ${price}.")
		}
		override fun onFall(price:Int){
			println("fell to ${price}")
		}
	}


	//使用
	val su =StockUpdate()
	val sd =StockDisplay()
	su.listeners.add(ad)
	su.price=100
	su.price=98
	```

实现Observer接口只能覆写update方法来编写相应逻辑，
如果存在过多不同的逻辑响应，我们必须通过该方法进行区分实现,
而使用Delegates.observable () 方法更加灵活；


### 2.1.2 Vetoable
有时我们不希望监控值可以随心所欲地修改，你希望对某些该值进行rejected，
Kotlin标准库除了提供abservable委托属性外，
还提供 vetoable，在被赋值生效之前提前进行截获，然后判断是否接收；

```
var value:Int by Delegates.vatoable(0){prop,old,new-> new>0}

//
value=1

value=-1
```


## 2.2 高级函数简化策略模式、模板方法模式
两种模式解决的问题比较类似
## 2.2.1 开闭原则 
```
class Swimmer{
	fun swim(){
		println("I am swimming....")
	}
}
```

有学会了蛙泳、仰泳、自由泳多种姿势
```
class Swimmer{
	fun breaststroke(){
		println("I am swimming....")
	}
	...
	fun freestyle(){
		println("I am freestyle....")
	}
}
```

### 2.2.2  策略模式
上面这种并不是好的设计：
并不是所有的运动员都掌握了者三种姿势，这比较危险；
后续难免会增加新的方法，通过修改 Swimmer 违背了开闭原则

更好的设计将游泳这个行为封装成接口，根据不同的场景可以调用不同的游泳方法；

策略模式定义了算法族，分别封装起来，让他们之间可以相互替换，
此模式让算法变化独立于使用算法的客户。

本质上，**策略模式将不同的行为策略进行独立封装，与类在逻辑上解耦，
然后根据不同的上下文切换选择不同的策略**，然后用类进行调用：
```
interface SwimStrategy{
	fun swim()
}
class Breaststroke:SwimStrategy{
	override fun swim(){
		println("I am breaststroking...")
	}
}

//其他游泳策略
...

//游泳运动员
class Swimmer(val strategy:SwimStrategy){
	fun swim(){
		strategy.swim()
	}
}

//调用
val weekendShaw =Swimmer(Freestyle())
weekendShaw.swim()


```
### 2.2.3 高级函数定义策略模式
将策略封装成一个函数然后作为参数传递给Swimmer类 会变得简洁。
策略模式目的仅仅是针对行为算法的一种抽象，所有高级函数是一种很好的替代思路：
```
fun breaststroke(){pringln("I am breaststroke...")}
...
fun freestyle(){pringln("I am freestyle...")}


class Swimmer(val swimming:()->Unit){
	fun swim(){
		swimming()
	}
}
```

### 2.2.4 高级函数定义模板方法模式
高级函数定义代替继承

模板和策略都可以分离通用的算法和具体的上下文，
如果说策略采用的思路是将算法进行委托，
那么传统的模板方法更多是居于继承方式实现

模板方法模式：定义一个算法种的操作框架，而将一些步骤延迟到子类种，
使得子类可以不改变算法的结构即可重新定义该算法的某些特点步骤；

与策略模式不同，模板方具有更明晰的大概结构，其中相同的步骤会在抽象类种实现，
可个性化的某些步骤则在其子类种进行定义。

比如：取市民事务中心办事：
a. 排队取号等待
b. 根据自己的需求办理个性化业务；
c. 对服务人员的态度进行评价

模板方法模式的代码复用率已经很到了，
但还得根据不同的业务场景都定义一个具体的子类
幸运的是 ：Kotlin 依靠高阶函数可以代替继承实现同样的效果:
```
//定义模板_ 定义算法框架
class CivicCenterTask{
	// 特定步骤参数传入
	fun execute(askForHelp:()->Unit){
		this.lineUp() //排队取号
		askForHelp()  //业务
		this.evaluate()//评价
	}
}

//定义特定步骤
fun pullSocialSecurity(){
	pringln("ask for pulling the social security")
}
...

//使用
val task1 =CivicCenterTask()
task1.execute(::pullSocialSecurity)

```

## 2.3 迭代器模式
定义某些容器类，类中包含大理相同类型的对象，给容器类的对象直接提供迭代方法，那么可以自定义一个迭代器，
通常我们不需要自己实现一个迭代器，java标准库提供了 java.util.iterator接口，容器类实现该接口，即可；

这种设计模式就是迭代器模式，其核心是**将遍历和实现分离**开来，在遍历的同时不需要暴露对象的内部结构。

### 2.3.1 实现iterator接口
```
data class Book(val name:String)

class Bookcase(val books:List<Boot>):Iterator<Book>{
	private val iterator:Iterator<Book>
	
	init{
		this.iterator=books.iterator()
	}
	override fun hasNext()=this.iterator.hasNext()
	override fun next() =this.iterator.next()
}
```


### 2.3.2 操作符重载实现iterator
```
class Bookcase (val books:List<Book>){
	operator fun iterator():Iterator<Book>=this.books.iterator()
}
```

### 2.3.3 扩展函数
假设Book和Bookcase是一个引入的类，不能修改他的源码，且没有实现迭代器，
我们可以通过扩展函数来对其增加迭代器方法：
```
//第三方库中的代码
data class Book(val name:String)
class Bookcase(val books:List<Book>){}

//自己的代码
operator fun Bookcase.iterator():Iterator<Book>=books.iterator()

//如果对迭代器中需要更多的权限控制可使用object 表达式来实现：

operator fun Bookcase.iterator():Iterator<Book>=object:Iterator<Book>{
	val iterator=books.iterator();
	override fun hasNext()=iterator.hasNext()
	override fun next()=iterator.next()
}
```

## 2.4 责任链模式-- 偏函数
在java里 Servlet 中的Filter和FilterChain接口，他们就是采用责任链设计编写的，
接收到一个web请求时，先进行各种filter逻辑操作，filter都处理完后，才执行servlet，
不同的filter代表了不同职责，最终形成一个责任链；

责任链模式的目的：避免请求的发送者和接收者间的耦合关系，将这个对象连成一条链，
沿着链传递该请求，直到有个对象处理它为止；

例如：学生成立基金会，如果支出金额在100元内，由各各个分部长审批，超过100 会长审批，超过500，辅导员老师审批，不宣规定，超过1000，打回申请；

```
//申请事件
data class ApplyEvent(val money:Int,val title:String)

//申请处理
interface ApplyHandler{
	//后继者
	val successor:ApplyHandler?
	fun handleEvent(event:ApplyEvent)
}
//部长审批
class GroupLeader(override val nextHandler:ApplyHandler?/*可空的后继处理者*/):ApplyHandler{
	override fun handleEvent(event:ApplyEvent){
		when{
		    //在部长权限内
			event.money<=100->{ println("签字${event.money}")}
			//不在 给其他人处理
			else -> when(successor){
				is ApplyHandler ->nextHandler.handleEvent(event)
				else -> { println("未能处理")}
			}
		}
	}
}
// 
...
//不宣规定
class College(...)..{
... 
	when{
		event.money>1000 -> pringln("不同意")
		else ->pringln("College Handled application :$(event.title).")
	}
...
}

//使用
val college = College(null)
val president =President(college)
val grouplead=GroupLeader(president)

grouplead.handleEvent(ApplyEvent(200,"team building"))
```

这个链条的每个处理环节都有对其输入参数的校验标准，当输入参数处于某个责任链环节有效的范围内，
该环节才对其做出正常的处理操作：
在编程语言中，我们有个专门的属于来描述这种情况：**偏函数**

实现偏函数的类型： PartialFunction
偏函数是数学中的概念：定义域X中可能存在某些值在值域Y中没有对应的值；

比如下面函数：
```
fun mastGreaterThan5(x:Int):Boolean{
	if(x>5) return true
	else throw Exception("X muse be Greator than 5")
}
```

Kotlin 标准库中没有定义，在开源库 funKTionale 已经实现了PartialFunction的定义：
```
class PartialFunction<in P, out R>(private val defineAt: (P) -> Boolean, private val f: (P) -> R) : (P) -> R {
  override  fun invoke(p1: P): R {
        if (defineAt(p1)) return f(p1)
        else throw IllegalArgumentException()
    }

    fun isDefinedAt(p1: P) = defineAt(p1)
}
```

利用扩展函数给PartialFunctino类增加一个orElse方法
```
infix fun <P1,R> PartialFunction<P1, R>.orElse(that:PartialFunction<P1,R>):PartialFunction<P1,R> {
	 return PartialFunction({ this.isDefinedAt(it)|| this.isDefinedAt(it)}) {
		 when {
			 this.isDefinedAt(it) -> this(it)
			 else -> that(it)
		 }
	 }
} 
```

在orElse 方法中，传入了一个 对象 that 是责任链模式的 后继者，当 isDefinedAt 执行结果未false 调用that对象来基础处理请求


```
data class ApplyEvent(val money:Int,val title:String)

val grouplead={
	val defineAt:(ApplyEvent)->Boolean ={it.money<=200}
	val handler:(ApplyEvent)-> Unit={ println("sign name")}
	PartialFunction(defineAt,Handler)
}()
...
val college={
	val defineAt:(ApplyEvent)->Boolean ={true}
	val handler:(ApplyEvent)-Unit={ 
		when {
			it.money>1000 -> println("拒绝")
			else ->println("College handle application:${it.title}")
		}
	}
	PartialFunction(defineAt,Handler)
}()

//使用
val  applyChain= groupLeader orElse president orElse college

```

借助 偏函数的封装，不仅大幅度减少程序代码量，而且可以使用orElse获得更好的语法表达；


## 2.5 状态模式--- ADT
ADT ： 用它可以结合模式匹配来抽象业务，ADT是函数式语言的一种强大的语言特性；

状态模式与策略模式存在某些相似，他们都可以实现某种算法，业务逻辑切换；
策略模式通过客户端切换不同的策略实现来改变算法，
而状态模式：对象通过修改内部状态来切换不同的行为方法；


状态模式：允许一个对象在内部状态改变时改变它的行为，对象看起来似乎修改了它的类；

状态模式具体表现在：
- 状态决定行为
- 对象的状态在运行期间被改变，它的行为也会因此而改变，

## 3.1 装饰模式 -类委托 减少样板代码

### 3.1.1 类委托
在java 中给一个类扩展行为的时候，通常由两种选择：
- 设计一个继承它的子类
- 使用装饰模式对类进行装饰，然后对功能进行扩展


目前为止不是所有的场合都适合采用继承的方式来满足类扩展的需求（里氏替换原则）
很多时候使用装饰者成了我们解决此类问题更好的思路

定义: 在不改变原类文件和继承的情况下，动态地扩展一个对象的功能，
该模式通过创建一个包装对象，来包裹真是的对象；

装饰模式步骤：
- 创建装饰类包含一个需要被装饰的类的实例
- 重写所有被装饰类的方法
- 在装饰类中对需要增加的功能进行扩展

可以看到装饰模式很大的有时在于符合“组合优于继承”的设计原则，规避了某些场景下继承所代理的问题；
然而有时显得比较啰嗦，重写装饰对象的方法，可能存在大理的样板代码

在Kotlin中可以让装饰模式的实现变得更加优雅 ---委托类特性

```
interface MacBook{
	//预算
	fun getCost():Int
	//机型
	fun getDesc():String
	//生产年份
	fun getProDate():String
}
class MacBookPro:MacBook{
    override fun getCost()=10000
    override fun getDesc()="MacbookPro"
    override fun getProDate()="Late2011"
}

//装饰类
class ProcessorUpgradeMacBookPro(val macBook:MacBook):MacBook by macBook{
    override fun getCost()=macBook.getCost()+219
}

```

ProcessorUpgradeMacBookPro 类会把MackBook接口所有的方法都委托给构造参数对象 macbook，我们执行通过覆写 需要变更的方法，其他的 自动调用封装了的方法；
