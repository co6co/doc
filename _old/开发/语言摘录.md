# 1. 《Kotlin核心编程》
如果说面向对象是归纳法，侧重于对事物特征的提取及概括，那么函数式编程中的组合思想则更像是演绎法，近似于数据中的推到。

心智的活动，除了尽力产生各种简单的认知外，主要表现在如下3个方面：
1. 将若干简单的认识组合为一个复合认识，如此产生出各种复杂的认识；
2. 将两个认识放在一起对照，不管他们如何简单或是负责，在这样做时并不将他们合二为一；如此得到有关他们的相互关系的认识；
3. 将有关认识在那些实际中和他们同在的所有其他认识隔离开，这就是抽象，所有具体普遍性认识都是这样得到的；

<hr />

1. 从设计角度而言，语句的作用服务于创建副作用的，表达式的目的则是创造新值；在函数式编程中，原则上表达式是不允许包含副作用的。
2. 函数式编程侧重于组合，尤其是很多高阶函数，源代码实现都采用泛型来实现；
3. 子类应该尽量避免重新父类的非抽象方法，因为一定父类变更方法，
   子类的方法调用很可能出错，重写父类非抽象方法违背了面向对象设计原则“李氏替换原则”
   子类可以扩展父类的功能，但不能改变父类原有的功能：
   - a. 子类可以实现父类的重新方法，但不能覆盖父类的非重新方法；
   - b. 子类可以增加自己特有的方法；
   - c. 当子类的方法实现父类的方法时，方法的前置条件（方法形参）要比父类方法的输入参数更宽松；
   - d. 当子类的方法实现父类的方法时，方法的后置条件（方法返回值）要比父类更严格；
4. 实际业务开发中我们常常很容易违背李氏替换原则，其根本原有是，我们一开始并没有仔细考虑一个类的基础更新；

5. 对开发者而言，业务需求总是在不断变动的。在修改现有代码的时候，我们应遵循开放封闭原则，即
软件实体应该是可扩展的，而不可修改的，
开放封闭原则（OCP，OPEN Closed Principle）是所有面向对象原则的核心。软件设备本身所追求的目标就是封装变化、降低耦合，而开闭原则正式这一目标最直接体现。
其他设计原则，很多时候是为了实现这一目标服务的，如替换原则实现最佳的、正确的继承层次，就能保证不会违反开闭原则。

实际情况并不乐观，比如我进行Android开发的时候，为了实现某个需求，我们引入了一个第三方库，但某天需求发生了变动，当前库无法满足，且库的作者暂时没有升级的集合。
这是也许你会尝试对库源码进行修改，这就违背了开放封闭原则，醉着需求的补丁变更，问题可以就会如滚雪球般增长。

Java 中一种惯常的应对方案是让第三方库类继承一个子类，然后增加新功能。然而、这样强行继承可能违背“里氏替换原则”
更合理的方案是依靠扩展这个语言特性，通过扩展一个类的新功能无需继承该类，在大多情况下都是一种更好的选择，从而我们可以合理地遵循软件设计原则。
